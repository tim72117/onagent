# version-tagging

打版號不是「挑一個沒用過的數字」，版號本身要能讓人（或下游 AI 代理）從版號**推斷出這次改動的破壞性程度**，且必須與 `CHANGELOG` 的實際內容一致。

## 適用範圍

- 每一次 `git tag` 建立新版號，不限本專案。
- 不含分支管理、stash 處理、合併衝突排除——那些是 git 操作紀律，不是版號慣例。

## 核心規則

### 1. 版號要先看 CHANGELOG，不要先看數字

打 tag 前，**先確認 `CHANGELOG`（或等效的異動記錄）已經寫好且涵蓋這次要發布的範圍**。版號是 CHANGELOG 內容的摘要，不是反過來——不要先決定「這次是 v0.2.0」再回頭湊理由。

若專案沒有 CHANGELOG 習慣，這件事本身就是該先指出的缺口，而不是跳過直接打 tag。

### 2. semver 在 0.x 階段的判斷

專案仍在 `0.x`（尚未宣告穩定 API）時，語意化版本沒有強制規則，但業界慣例：

| 變動類型 | 建議升版位置 | 理由 |
|---|---|---|
| 破壞性變更（移除/改名公開符號、改變呼叫方式） | 升 **minor**（`0.1.0` → `0.2.0`） | `0.x` 沒有 major，minor 承擔「不相容變更」的訊號 |
| 新增功能、不影響既有呼叫方式 | 升 minor 或 patch 均可，依專案慣例 | |
| 純修 bug、無 API 變動 | 升 **patch**（`0.1.0` → `0.1.1`） | |

**判斷「是否破壞性」的方法**：檢查是否有公開符號（型別、函式、方法、欄位）被移除、改名，或呼叫方式改變到舊程式碼編譯不過。若有，即為破壞性，不論改動規模大小。

### 3. Annotated tag 的訊息要含破壞性變更摘要

用 `git tag -a`（不要用 lightweight tag），訊息至少包含：

- 一行標題：版號 + 這次變更的主題
- 破壞性變更清單（若有）：逐條列出被移除/改名的符號，簡短說明替代方案指向哪裡（例如指向 CHANGELOG 的具體檔案）

不要只寫「bug fixes」「various changes」這類無資訊量的訊息——tag 訊息常是下游使用方唯一會看到的一手資料，尤其是自動化升級工具。

### 4. 固定順序：讀差異 → 查過時 → 修正 → 寫 CHANGELOG → commit → 打 tag

這五步有嚴格的先後關係，不可以顛倒或跳過，尤其不要「先寫 CHANGELOG 再順便看看有沒有過時」——順序反了會把還沒查證過的內容當成正式記錄寫出去。

**Step 1：讀取這個版本的完整差異**

以「上一個已發布 tag 到現在 HEAD」為範圍取完整 diff（`git diff <上個tag>..HEAD` 或逐 commit 讀），而不是只看最新一次 commit 的訊息或憑印象。逐一檢查所有公開符號層級的變化（型別、函式、方法簽名、欄位的新增/移除/改名/簽名變更），漏看任何一個 commit 都可能漏掉一個破壞性變更——尤其當這個範圍內有多個 commit（例如 rebase、多次修補疊加）時，每個 commit 各自的變更都要核對，不能只看合併後的最終狀態就假設沒有中間被忽略的符號變化。

**Step 2：查對應文件與註解是否過時**

CHANGELOG 描述的是「程式碼實際做了什麼」，而註解、docstring、README 這類文件常常滯後於程式碼——上一版遺留的過時描述會被誤當成現況。對 Step 1 找出的改動觸及、或改動影響到其行為的模組，檢查其註解/文件是否仍與程式碼一致：

- 找「宣稱現況」的描述句（如「目前僅…」「尚未…」「已遷移至…」），逐一核對對應程式碼是否還是那樣
- 找文件裡引用的具體檔案路徑、函式名、符號名，確認它們仍然存在且指向正確位置

範圍拿捏：不必逐檔通讀整個專案，聚焦本次變更的模組與其直接依賴方即可；若專案本身就在做全面文件盤點，可以視為這一步的延伸。

**Step 3：修正過時內容**

Step 2 找到的過時描述，在寫 CHANGELOG 之前先修正（或至少在程式碼裡標註清楚待修）。不要帶著已知的過時內容繼續下一步——那會讓錯誤描述被 Step 4 的 CHANGELOG 當成事實引用。

**Step 4：產生 CHANGELOG**

基於 Step 1 的完整差異（修正後的版本）寫 CHANGELOG，不是基於記憶或單次 commit 訊息。確認涵蓋這次要發布的整個範圍，不只是最新一次 commit。若專案沒有 CHANGELOG 習慣，這件事本身就是該先指出的缺口，不要跳過直接打 tag。

**Step 5：把 Step 3 的修正與 Step 4 的 CHANGELOG 一併 commit**

過時內容的修正、新增的 CHANGELOG 檔案，必須在打 tag 前完成 commit——tag 指向的 commit 若不包含這些修正，等於過時內容仍隨這個版本一起發布出去，Step 2-3 等於做了白工。

**Step 6：打 tag**

指向 Step 5 commit 之後的 HEAD。

### 5. 打 tag 前的最後檢查

- CHANGELOG 的破壞性變更清單，跟即將打的版號是否一致（如果 CHANGELOG 有 breaking change 但版號只升 patch，先問清楚再繼續，不要自行決定哪個是對的）
- tag 訊息裡提到的檔案路徑（如 CHANGELOG 條目）確實存在、內容確實對得上
- 第 4 條 Step 1-5 已經完整跑過一輪：差異讀了、過時查了、修正做了、CHANGELOG 寫了、且**修正與 CHANGELOG 已經 commit**——不是還停在工作目錄的未提交狀態

## 不做的事

- 不自動 push tag 到遠端——tag 建立與推送是兩個決策，推送前應徵求確認。
- 不在版號判斷有疑義時自行拍板（例如破壞性程度介於 minor/patch 之間）——列出兩種判斷的依據，讓使用者選。
