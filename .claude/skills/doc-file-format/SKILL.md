# doc-file-format

在 `docs/` 底下建立或更新任何文件前，先套用這份 skill 判斷檔名、目錄、內部結構規則。`docs/` 底下的文件依性質分成三種字首，彼此的更新方式、是否帶日期、內部結構都不同，混用會讓文件失去原本該有的可維護性。

## 目錄規則

**目錄固定用 `docs/`（複數）**，符合本專案現況；不要用 `doc/`（單數）。

## 三種文件字首

建立新文件前，先判斷內容屬於哪一種，不要混用：

### `audit-*` — 稽核報告（持續追蹤，不帶日期）

用於安全掃描、功能/程式碼品質掃描、並發/穩定性掃描的**結果報告**。內容要能跨越多次複核持續更新現況，不是一次性快照。

- **主檔名一律以 `audit-` 開頭**，後接稽核類型，**不帶日期**：
  - **`docs/audit-security.md`** — 安全稽核（漏洞、認證/授權、注入、機密外洩等安全相關發現）。
  - **`docs/audit-functional.md`** — 功能/架構稽核（命名不一致、死碼、遷移殘留、邏輯錯誤、架構債、程式碼品質等非安全、非並發性發現）。
  - **`docs/audit-stability.md`** — 並發/穩定性稽核（race condition、deadlock、goroutine 洩漏、panic/crash 風險、資源未清理等無安全後果的並發或穩定性問題）。
- 三者判準邊界：
  - 一個問題**只要有安全後果**（未授權存取、機密洩漏、跨使用者資料污染、執行非預期命令），即使根因是並發缺陷（例如 EventBus 退訂失效造成跨連線事件串話），也優先歸類到 `audit-security.md`；`audit-stability.md` 只保留該問題**純並發/正確性根因本身**（不涉及安全後果的部分），並在項目中交叉引用對方檔案，不重複收錄同一後果。
  - 純命名、死碼、型別設計、遷移殘留等**靜態程式碼品質**問題歸 `audit-functional.md`；**執行期行為**（race、deadlock、panic、goroutine/資源洩漏、逾時缺失）歸 `audit-stability.md`。兩者偶有重疊（例如「未檢查的型別斷言」既是程式碼品質問題也可能導致 panic），依「這次要修的是哪個面向」判斷主要歸屬，並在項目中註明另一面向。
- 不帶日期是因為內容要靠「進行中的發現」持續更新現況（見下方內部結構），不是每次稽核都產生一份新的一次性報告。
- 若某次稽核的某個嚴重度分級內容多到必須拆成獨立檔案（例如高/中/低各自成檔），延伸檔沿用相同字首、以嚴重度分級再加一段，例如 `docs/audit-security-medium.md`、`docs/audit-security-low.md`；主檔（`docs/audit-security.md`）仍是預設優先合併回單一檔案的目標，只有內容量體確實過大、單一檔案難以維護時才拆分，且拆分後仍要在主檔開頭列出延伸檔連結。

### `research-*` — 研究/調查筆記（一次性，帶日期）

用於針對某個主題的探索、調查、方案比較，例如 `research-architecture-ideas-2026-07.md`、`research-observability-2026-07.md`。

- **檔名帶日期**（`-YYYY-MM` 或 `-YYYY-MM-DD` 後綴），因為這類文件是特定時間點的產出快照，內容定案後不常回頭改；若之後有新一輪研究，建立新日期的新檔案，不要覆寫或往舊檔案裡疊加「更新」章節。
- 若研究結論後續變成要執行的規劃，另開一份 `refactor-*` 文件承接，`research-*` 原文保留不動作為歷史紀錄。

### `refactor-*` — 重構/實作規劃（一次性，帶日期）

用於具體的重構、遷移、新功能實作計畫，例如 `refactor-strategy-2026-07.md`、`refactor-config-storage-injection-plan-2026-07.md`。

- **檔名帶日期**，理由同 `research-*`：規劃定案後是特定版本的執行藍圖，不是持續更新的活文件。規劃執行完成或作廢後，在檔案開頭加註現況（完成/取消/被取代），不要刪除，以保留決策軌跡。

### 三者的核心區別

`audit-*` 是**持續追蹤、每次複核都要回來更新現況**的活文件，因此不比照帶日期，避免產生「audit-security-2026-07.md」「audit-security-2026-08.md」這種本質上該是同一份文件卻被日期拆散的情況。`research-*`、`refactor-*` 則是**一次性快照**——研究結論或規劃內容一旦寫定通常不會逐次回頭改寫，所以帶日期做版本區隔是合理的，新一輪研究/規劃就開新檔案，不與舊檔案混寫。

## `audit-*` 專屬規則

以下規則只適用於 `audit-*` 稽核報告，`research-*`／`refactor-*` 不適用（它們是一次性文件，沒有「持續更新現況」的需求）。

### 檔案分工

三種稽核各自獨立一份檔案，不要混在一起（檔名見上方「三種文件字首」）：

- 「深度安全掃描」「security review」「安全稽核」之類 → 寫 `audit-security.md`
- 「掃描潛藏錯誤」「功能稽核」「找 bug」（命名/死碼/架構債等靜態問題）之類 → 寫 `audit-functional.md`
- 「並發稽核」「穩定性稽核」「race condition 檢查」「-race 複測」之類 → 寫 `audit-stability.md`

多種都要做時，對應的檔案都更新，不要合併成一份。

如果對應的檔名在專案裡还不存在（例如專案原本只有一份混合的 `project-audit.md`，或分散在多份帶日期的舊檔案如 `security-audit-2026-07.md`、`concurrency-audit-2026-07.md`），先把舊內容依安全 vs. 功能 vs. 並發/穩定性三類拆分/合併成對應檔案，再繼續套用下面的更新規則。搬移時保留舊檔案原本的發現內容與行號引用，不要重寫或簡化；搬移完成後，找出其他文件中指向舊檔名的連結一併修正，並刪除舊檔案，不要讓新舊檔案並存造成日後對不上。

### 檔案內部結構

每份稽核檔案固定分成三大塊，由上到下：

1. **最新掃描結果**（檔案最上方）——這次稽核新產出的內容，包含掃描日期、方法摘要、以及**只在這次才第一次發現**的項目。
2. **進行中的發現**（依嚴重度排序）——所有還沒解決、跨越多次稽核持續追蹤的項目。每個項目底下用「現況（YYYY-MM-DD 複核）」記錄最新一次複核的結果，不要另開新章節重複整份項目描述。
3. **已複核為安全/已解決的項目** — 曾經是關注項目、現在確認沒問題或已修復的，移到這裡並簡述何時確認、為什麼。

### 核心規則

#### 1. 新掃描結果放最上方，不是附加在檔案最後

每次執行新的稽核，把「最新掃描結果」整個區塊換成這次的內容，放在檔案最上方（在稽核慣例說明之後、進行中發現之前）。不要在檔案尾端一直往下疊加「2026-08-16 複掃」「2026-08-20 複掃」這種歷史章節——舊的複掃記錄本身不需要保留成獨立章節，它的**結論**要合併進第 2 點的「進行中的發現」。

#### 2. 舊發現要「更新現況」，不要「新增重複區塊」

一個項目（例如 S2、S3 這類編號發現）如果在上一次稽核就存在，這次複核後：

- 找到它原本在「進行中的發現」裡的段落
- 在段落底下用一行「**現況（YYYY-MM-DD 複核）**：...」更新最新狀態（仍未修復 / 已修復 / 部分修復 / 嚴重度調整）
- **不要**複製一份完整的舊描述到新的「最新掃描結果」區塊裡再說一次「仍未修復」——那是重複記錄，日後兩處會對不上

只有「這次稽核才第一次發現」的新項目，才寫進最上方的「最新掃描結果」區塊；等下一次稽核，這些新項目也要併入「進行中的發現」，用同樣的「現況（日期複核）」方式維護。

#### 3. 已解決的項目要移動，不要留在原地打勾

項目一旦確認修復（程式碼複核 + 建議做一次功能驗證），從「進行中的發現」移到「已複核為安全/已解決」區塊，附上修復的簡述與確認方式（複核程式碼 or 實測）。不要留一個「✅ 已修復」的項目繼續待在進行中清單裡佔位置。

#### 4. 保留原始的具體內容

- 檔案位置引用（`file:line`）、攻擊情境/repro 情境、修法建議——這些具體內容在合併/更新時要保留，不能因為「整理格式」而濃縮成一句話摘要。
- 嚴重度標記維持 🔴 critical｜🟠 high｜🟡 medium｜⚪ low 四級。
- 每份檔案開頭維持一段稽核慣例說明（本 skill 內容的濃縮版即可），讓之後接手的人不用來讀這份 skill 也知道格式規則。

#### 5. 掃描方法要註明，但不用逐次保留舊方法說明

每次「最新掃描結果」區塊要註明這次用的方法（例如：幾個 agent、哪些對抗式驗證流程、掃描範圍）。上一次的方法說明在被併入「進行中的發現」時可以捨棄，不用逐字保留——方法本身不是要追蹤的狀態，只有結論才是。

### `audit-*` 不做的事

- 不要把安全、功能、並發/穩定性三類發現寫進同一份檔案。
- 不要用「複掃更新」「2026-08-16 更新」這種日期章節在檔案裡累加——超過一次之後，同一個項目的歷史會散落在多個章節，難以看出目前真正的狀態。
- 不要在標記「已解決」前只憑掃描 agent 的說法就下結論——比照 [[project_want_registry_bug]] 這類記憶裡記載過的教訓，遇到「schema/設定改了但沒生效」這類情況要先懷疑是不是有 registry/cache 沒重新載入，而不是照單全收「已修復」的判斷。
