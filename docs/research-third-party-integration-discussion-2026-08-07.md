# 第三方 Support-Ops Console 整合設計討論：Auth、併發與配額

本文件記錄一場由三個角色參與的架構討論，主題是將某第三方開發者的 support-ops console 產品與 onagent 後端整合。討論需求最初由該第三方開發者提出，並在討論過程中由另外兩位參與者（系統架構師與資深工程師）進一步釐清與擴充。以下內容為逐字保留的討論過程，以及討論結束後整理出的結論。

## 參與角色

- **第三方軟體開發者 (Third-party developer)**：正在打造 support-ops console 並想在其中加入 AI copilot 的產品方，關注 auth 威脅模型、併發上限、配額可見性等能否支撐正式上線的實務問題。
- **系統架構師 (Systems architect)**：從 onagent 系統設計角度回應，釐清 auth/origin 模型的既有邊界，並指出 `GlobalEngine` 併發架構的限制與尚待 onagent 內部解決的容量問題。
- **資深工程師 (Senior engineer)**：熟悉 onagent 程式碼實作細節，負責修正機制上的誤解（如 auth 的實際解析方式）、給出具體協定層級的建議（tool kind 劃分、error code 補強）與可行的過渡方案。

## 討論過程

**[第三方軟體開發者 (Third-party developer)]:**
我們正在打造一個 support-ops console——想像成一個共用收件匣，加上每個客戶帳號狀態（訂閱方案、權限、近期錯誤）的即時檢視畫面，我們的客服人員整天都在用這個介面。我們想在同一個頁面裡加裝一個 AI copilot，讓它能做三件事：(1) 透過我們的內部 API 拉出客戶帳號摘要、(2) 在我們的編輯器裡預先填好建議的回覆草稿、(3) 在我們自己的系統裡建立或更新工單狀態——也就是三個 tool call，全部都在我們自己的技術堆疊上執行，不是你們的。

在往下談之前——有幾件事我需要先搞清楚。第一，auth：我看到 API key 是透過 WS URL 上的 `?token=` 傳遞的。我們自己這端是多租戶的——有幾百個客戶組織，每個客服人員都登入我們自己的應用程式。onagent 的 API key 是綁定在我們的 app 層級（一把 key，所有使用者共用一個 session pool），還是你們預期我們要幫每個終端使用者各自發一把？這會直接影響我們在瀏覽器端處理 key 的威脅模型。

第二，負載：實際的併發上限是多少？如果我們有十個客服人員同時發出 prompt，他們會排隊等待嗎？那種情況下實際的 p95 延遲大概是多少？

第三，配額——配額是不是以我們的帳號為單位統一計算，不管是哪個客服人員在用？我們能不能用程式化的方式查詢剩餘配額，這樣才能優雅地顯示「AI copilot 目前無法使用」，而不是讓它默默失敗？

**[系統架構師 (Systems architect)]:**
先講 auth：幫每個終端使用者各自發 key，不要整個組織共用一把。目前一把 API key 會解析成唯一一個 `appID`，並綁定一個 origin allowlist（`auth.Store.Verify`、`handler.go:94-127`）——key 裡面沒有「次主體」的概念。如果你把同一把 key 嵌進每個客服人員的瀏覽器 session，任何一個能打開開發者工具的客服人員都能把它偷出來、無限制地開啟 session 消耗你們的配額——一把 key 外洩的影響範圍是你們**整個組織**的推論預算，不是單一客服人員的份額。幫你們後端的每個使用者各自發一把 onagent app-key（或者用代理模式：你們的後端持有真正的 key，依每次客服人員登入發放短效、限定範圍的 token）——這是你們自己這端要做的決定，onagent 不會替你們做終端使用者層級的 auth。

關於 origin：不管客服人員在看哪個客戶組織的資料，你們都是同一個網站，所以幫你們的 console 網域設一筆 `APP_ORIGINS` 項目就對了——不用在這裡想太多多租戶的問題，這是你們自己後端資料層的事，不是 WS-origin 層級的事。

併發——這才是你該更擔心的地方：目前系統裡有一個 process 層級的 `GlobalEngine`，裡面是**併發數=1 的請求佇列**，同一個 instance 上的所有 session 都共用它（`want.go:26-46`）。十個客服人員同時發送不會平行處理——會全部排在同一個佇列後面，每個都受限於 90 秒的 `completeTimeout`。最差情況下 p95 可能是好幾個人排隊的延遲疊加。這是 onagent 主機容量層級的問題，不是你們架構上能解決的事——但你們需要在上線前拿到具體數字，而不是等尖峰時段才發現。

配額：對，是以 `apps.owner_id` 為單位統一計算的——但目前沒有查詢用的 API，只有連線握手時的 429，跟連線中途的 `error{code:quota_exceeded}`。你們得自己在前端追蹤消耗量，或是要求 onagent 提供一個用量查詢 API。

**[資深工程師 (Senior engineer)]:**
對，在繼續之前先糾正一個 auth 機制上的認知：onagent 的 API key 完全沒有「使用者」這個概念——它是透過 `auth.Store.Verify(token)` 解析成唯一一個 `appID`，就這樣，而且解析出來的 `appID` 永遠會覆蓋掉你們 `hello` payload 裡宣稱的 `appId`（`handler.go:94-127`、`session.go:194-202`）。所以「每個終端使用者一把 key」這個概念完全是你們自己這端建構出來的假象——onagent 沒有辦法區分客服人員 A 的 key 跟客服人員 B 的 key，唯一的差別只是它們是打在同一個 origin allowlist 上的不同 token。

具體到你們的流程：你們的後端在每次客服人員登入時發放一把短效的 onagent key，瀏覽器開啟 `wss://.../ws?token=<key>`，送出 `hello{appId, sdkVersion, pageUrl}`，收到 `ack{sessionId, toolNames:["get_account_summary","draft_reply","update_ticket"]}`。`get_account_summary` 應該設計成 `tool_query`（阻塞式——LLM 需要把真實資料拿回 context 才能開始草擬回覆）；`draft_reply` 跟 `update_ticket` 可以是 `tool_call`（發完即忘），因為你們不需要把結果餵回推論過程。這三個 tool 全部都在客服人員的瀏覽器裡、透過你們自己註冊的 handler map 執行——絕不會 eval，只會依名稱比對（`client.ts:277-291`）。

一個硬性要求：`Origin` 必須跟你們設定的 `APP_ORIGINS` 項目完全一致——不支援萬用字元，也不支援子網域比對。如果你們的 console 在不同環境下跑在多個子網域，就要各自設定明確的項目，不能用一個 pattern 概括。

**[第三方軟體開發者 (Third-party developer)]:**
Auth 模式沒問題——代理發放短效 token、依每次客服人員登入各自發放，我們可以做到，我們後端本來就會幫自己的應用程式發 session token，這只是流程裡多加一個 claim 而已，不算大工程。

併發是讓我比較擔心的部分。一個 process 層級、併發數=1、90 秒 timeout 的佇列，意味著如果我有十個客服人員在用，就算只是幾個比較慢的 `get_account_summary` 往返疊在一起，某個人可能就要等上好幾分鐘才能拿到草擬回覆。這對一個即時運作的客服 console 來說不可行——我們的客服人員只要偶爾遇到隨機等了 90 秒，就會不再信任這個 copilot。我需要實際的數字：這個佇列是每個 instance 各自獨立的，還是你們在 WS endpoint 後面有水平擴展多個 instance？或者其實整個 onagent 機隊就只有一個佇列？如果是每個 instance 各自獨立，有沒有辦法保證我們的流量被釘選在某個專屬 instance 上，就算要多付費也行？我寧願花錢買一條可預期的專屬車道，也不要 best-effort 的共用容量。

還有——一個我剛才沒想到、現在才浮現的新需求：我需要一個前端可見的方式，區分「你們的佇列塞車了」跟「tool call 在我這端失敗了」跟「配額用完了」這三種情況。照現在的說法，推論變慢在前端看起來就是一個卡住的 prompt，一直到 90 秒 timeout 觸發前完全沒有任何訊號。`error` 能不能帶一個專門給佇列深度／timeout 用的 `code`，讓我可以顯示「AI copilot 忙線中，請稍後再試」，而不是讓我的介面看起來像壞掉了？另外附議用量查詢 API 這個需求——沒有它我沒辦法做出我們客服主管一定會要求的「本月剩餘 3 次」這種提示橫幅。

**[系統架構師 (Systems architect)]:**
只要兩個數字定案，我們就算是可以上線了，其他都已經有結論。

已定案：origin 模型——一筆 `APP_ORIGINS` 項目，就這樣。Tool kind 劃分——`get_account_summary` 是 `tool_query`，另外兩個是 `tool_call`——這是對的，不用再議。每人各自代理發放 token——已定案，這是你們後端的工作，你們也已經同意要做。

還沒定案的部分，而且我要修正我自己稍早的說法：「付費買一個專屬 instance」以 onagent 目前的樣子來說根本不存在這個選項。這個佇列活在一個 process 層級、用 `sync.Once` 初始化一次的 `GlobalEngine` 裡（`want.go:26-46`）——它不是依 app、依租戶，或依「你可以租用的 instance」去切分的。水平擴展意味著*更多的 process*，但每一個內部仍然是併發數=1 在序列化處理；就算 onagent 真的跑了好幾個 instance，目前也完全沒有任何路由層能把你的流量專屬釘選在其中一個上面。所以「專屬車道」是一個真實的需求，但它是 onagent 主機團隊的路線圖項目，不是你週一就能打開的設定開關。直接去問他們要 (a) 目前機隊層級的 instance 數量、以及 (b) 在你們上線日期前，能不能做出 app 釘選路由——不要讓這件事停留在含糊帶過的狀態。

關於你提的 error-code 跟用量查詢 API 需求：兩個都合理，而且目前協定裡都真的沒有（`protocol.ts:67-74` 沒有佇列深度訊號，`quota.go` 沒有查詢端點）。我會把這兩個當成上線前的阻塞性需求，不是可有可無的加分項——現在就把它們正式提出來，別等到出貨日才像今天發現佇列深度問題一樣才被發現。

**[資深工程師 (Senior engineer)]:**
在結束這個話題前，有兩件事要修正。

第一，error-code 這個需求其實比聽起來簡單——不用等一個全新欄位被設計出來。`error{message, code?}` 這個結構今天就已經在協定裡了（`protocol.ts:67-74`、`session.go:266-268`）；目前唯一會發出的 code 只有 `quota_exceeded`。缺少的只是*涵蓋範圍*，不是 schema 本身。我建議 onagent 出貨兩個具體的新增項目：`completeTimeout`（90 秒）觸發卻沒有回應時發 `code: "queue_timeout"`；等待你們瀏覽器端 handler 回應、20 秒的 `tool_query` 視窗過期時發 `code: "tool_query_timeout"`——後者對你們特別重要，可以區分出「是你們的 handler 卡住了」而不是「onagent 的佇列塞車」。這兩個都很便宜：這些 timeout 路徑伺服器端本來就已經存在，只是目前要嘛直接斷線、要嘛只回一個沒有型別的訊息而已。不需要改架構，只是把 enum 補齊。

第二，關於用量查詢 API——在它出貨之前，不要用猜測去做「剩餘 3 次」這種功能。用 `requestId` 當 key，在前端追蹤成功／失敗次數，對照你們已知的每月上限（免費方案 100 次，見 `plan.go:45-50`），因為用量本來就只會在推論成功之後才會記錄到伺服器端（`session.go:282-291`）。這樣你們就能有一個準確的本地計數器，不需要等新端點就能上線。

**[第三方軟體開發者 (Third-party developer)]:**
合理，這兩個都是低成本的解法，比起上線時什麼都沒有，我會先接受一個前端本地計數器——關於每月 100 次的預設值我記下了，我們會在本地計數器達到 80% 時顯示一個柔性警告橫幅，等真正的用量查詢 API 出來之後再校正。但麻煩把這個記錄成一個後續追蹤項目，不是「不會修」——本地追蹤的計數器只要使用者換了第二個瀏覽器分頁，或是我們後端重啟導致記憶體內狀態遺失，就會產生誤差，而且客服主管一定會比我們自己先發現這個問題。

`queue_timeout` 跟 `tool_query_timeout` 這兩個明確的 code 解決了我的介面狀態問題，同意——這正是「copilot 正在思考中，請稍等」跟「東西壞了，請重新整理」之間的差別。我現在就會照這兩個開始開發。

我還在意的是：目前還沒有人給我實際的機隊數字。「這是路線圖項目，去問主機團隊」作為下一步沒問題，但在我知道今天的答案是一個 process 還是十二個之前，我沒辦法承諾一個整合時程，因為那就是「偶爾變慢」跟「十個客服人員同時上線就整個不能用」之間的差別。在我把這件事排進我們自己的路線圖之前，我需要那個數字，加上 onagent 自己對這件事的錯誤預算／SLA 承諾——不然我等於是在打造一個客服主管在尖峰時段沒辦法信賴的 copilot，那比完全不上線還糟。onagent 這邊能不能有人這週就認領去把這個數字弄清楚給我？

## 結論

### 1. 已達成共識的架構

開發者的後端會依每次客服人員登入，各自發放一把短效、限定範圍的 onagent API key（代理模式——真正的 key 永遠不會直接發給瀏覽器）。瀏覽器開啟 `wss://.../ws?token=<短效key>`，送出 `hello{appId, sdkVersion, pageUrl}`，收到 `ack{sessionId, toolNames:["get_account_summary","draft_reply","update_ticket"]}`。三個 tool 全部都在客服人員的瀏覽器端、透過開發者自己註冊的 handler map 執行，實際操作對象是他們自己的內部 API／編輯器／工單系統——沒有任何東西跑在 onagent 的後端。這個設計完全不需要 onagent 那端有「終端使用者」的概念；多租戶（數百個客戶組織）完全是開發者後端資料層的事，對 onagent 來說是不可見的。

### 2. 已達成共識的協定／整合機制

- **Auth**：key 透過 `auth.Store.Verify` 解析成唯一一個 `appID`；解析出來的 `appID` 永遠會覆蓋 `hello` payload 裡宣稱的 `appId`（`handler.go:94-127`、`session.go:194-202`）。不支援次主體——「每人各自的 key」是開發者自己這端用不同 token 建構出來的概念，不是 onagent 的原生機制。
- **Origin**：console 網域設一筆 `APP_ORIGINS` 項目，僅接受完全比對，不支援萬用字元／子網域比對。多個環境／子網域需要各自明確設定多筆項目。
- **Tool kind**：`get_account_summary` → `tool_query`（阻塞式；結果必須先餵回 LLM context 才能開始草擬）。`draft_reply` 跟 `update_ticket` → `tool_call`（發完即忘）。
- **Error code**：`error{message, code?}` 這個結構在協定裡已經存在（`protocol.ts:67-74`、`session.go:266-268`）；目前只有 `quota_exceeded` 這一個 code 真的會被發出。雙方同意新增兩個上線前必須完成、低成本的 code（timeout 路徑本來就存在，只需要補上型別化的 code，而不是直接斷線或回傳無型別訊息）：`queue_timeout`（90 秒 `completeTimeout` 觸發時）與 `tool_query_timeout`（等待瀏覽器 handler 回應的 20 秒 `tool_query` 視窗過期時——代表是*對方*的 handler 卡住，不是 onagent 的佇列問題）。
- **配額查詢的過渡方案**：目前沒有查詢端點。開發者會用 `requestId` 當 key，在前端追蹤成功／失敗次數，對照已知的每月 100 次免費方案上限（`plan.go:45-50`）；用量只會在推論成功之後才會記錄到伺服器端（`session.go:282-291`）。開發者會在本地計數器達到 80% 時顯示柔性警告橫幅，供上線使用。

### 3. 已達成共識的安全要求

- 由開發者自己的後端依每次客服人員登入各自發放短效 token——絕不能把單一共用的 onagent key 嵌進所有客服人員的瀏覽器 session（一把共用 key 外洩的影響範圍等於整個組織的推論預算）。
- 強制要求 `wss://`（key 透過 query param 傳遞這個機制本身就隱含了這個要求）——絕不能用純 `ws://`。
- 強制執行完全比對的 `Origin`，每個環境／子網域各自一筆項目，設定在 `APP_ORIGINS` 裡。
- 前端絕不 eval 或動態派送 tool call——僅依名稱比對已註冊的 handler map（`client.ts:277-291`），這點在提案的設計裡已經滿足。

### 4. 明確列為未解決的事項

- **機隊容量數字**——尚未解決，且被開發者標記為上線前的阻塞項目。`GlobalEngine` 是一個 process 層級、用 `sync.Once` 初始化一次、併發數=1 的佇列（`want.go:26-46`）；它*無法*切分，且「付費買專屬 instance／車道」已確認**目前不存在這個選項**——即使 onagent 真的跑多個 process，目前也沒有任何路由層能把流量釘選在其中之一。架構師明確把這件事重新定位成 onagent 主機團隊的路線圖項目，不是一個設定開關。
- **開發者這週需要的兩個具體要求，目前尚未指派負責人**：(a) 目前機隊層級的 instance 數量，(b) 在開發者上線日期前，app 釘選／專屬車道路由是否做得出來，以及 (c) onagent 對併發數=1 佇列深度的 SLA／錯誤預算承諾。
- **用量查詢 API**——onagent 這方的兩個角色都承認這是一個真實存在的缺口（`quota.go` 沒有查詢端點），並明確記錄為後續追蹤項目，不是「用完就忘的權宜方案」；本地前端計數器只被接受為一個暫時的權宜之計，開發者也特別指出它在多分頁使用或後端重啟時會產生誤差。
