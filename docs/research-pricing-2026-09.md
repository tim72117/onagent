# onagent 定價方案草案（2026-09）

本文是定價的第一版討論稿，不是已定案的方案。市場行情取自 2026-09 的公開定價頁，
成本試算以 Gemini 3.1 Flash Lite 的 Google API 價格為基準
（輸入 $0.25／輸出 $1.50 每百萬 token）。

---

## 1. 起點與問題

初步構想是「**500 則 / $39 美元**」，其中「則」指一次請求。

這個定價的毛利完全站得住——但「請求」作為計價單位有問題，而且**這個專案先前就已經
否決過它**。`quota.Plan.MonthlyTokens` 的註解寫得很清楚：

> Replaces the earlier per-prompt-count model (MonthlyPrompts): a plan of N prompts
> was a poor proxy for actual LLM cost once a single prompt could trigger a variable
> number of internal provider round-trips (tool-calling loops) each with very
> different token weight.

也就是說，後端早就從「數次數」改成「數 token」，理由正是下面這一節要講的。

### 1.1 為什麼「一次請求」會誤導使用者

一次使用者發話，會觸發幾次 LLM round-trip 取決於這一輪呼叫了幾個工具。
以本專案部落格文章裡的沙龍助理為例，一輪對話跑了 `get_today_date`、
`check_availability`、`book_appointment` 三個工具：

| 每輪工具呼叫數 | 實際請求數 | $39 能對話的輪數 | 換算每輪售價 |
|---|---|---|---|
| 0（純問答） | 1 | 500 | $0.078 |
| 1 | 2 | 250 | $0.156 |
| 2 | 3 | 167 | $0.234 |
| **3（沙龍範例）** | **4** | **125** | **$0.312** |
| 5 | 6 | 83 | $0.468 |

**「500 則」在工具密集的場景其實只有 125 輪對話。** 買的人會以為是 500 次對話，
用起來只有四分之一，這是最容易引發客訴與退費的那種落差。

更糟的是它的**誘因方向相反**：工具用得越多、agent 越有用，額度消耗越快。
等於在懲罰使用者做 onagent 最擅長的事。

---

## 2. 成本結構

先確認成本，再談定價。以每則 3,000 token、輸入輸出比 2700:300 估算
（客服回應短、但每輪都要重送系統提示詞、工具定義與對話歷史）：

| 對話量 | token 總量 | LLM 成本 |
|---|---|---|
| 500 輪 | 1.5M | $0.56 |
| 5,000 輪 | 15M | $5.62 |

**成本低到幾乎不影響定價決策。** 以 $39 / 1.5M token 計，毛利率 98.6%；
即使每輪對話長度變成四倍（12,000 token），毛利率仍有 94%。
成本要到每則約 **20 萬 token** 才會吃掉 $39——實務上不會發生。

這代表**用量風險趨近於零**，定價可以純粹從價值與競爭出發，不必為成本保留緩衝。

### 2.1 可再降低成本的手段（暫不納入定價假設）

- **Context caching**：系統提示詞與工具定義每輪重送，快取後該部分是 $0.025/百萬
  （輸入價的 1/10），整體約可再省三到四成。但儲存費為 $1.00/百萬 token/小時，
  只有高頻使用才划算，額度分散在整個月時反而不利。
- **Batch API**：五折，但客服是即時對話，用不上。

## 3. 市場行情

### 3.1 AI 客服產品（按結果計價）

| 廠商 | 計價方式 | 費率 |
|---|---|---|
| Freshdesk (Freddy) | 每次 session | $0.10 |
| HubSpot Customer Agent | 每次成功解決 | $0.50 |
| Quickchat AI | 每次成功解決 | $0.50 |
| Gorgias | 每次成功解決（分級） | $0.60–1.27 |
| **Intercom Fin** | 每次成功解決 | **$0.99** |
| Zendesk AI | 每次成功解決 | $1.50–2.00 |
| Salesforce Agentforce | 每次對話 | $2.00 |

$0.99 是這個區隔的定錨價。但**這不是 onagent 的直接對手**——他們賣的是「客服結果」，
客戶是客服主管；onagent 賣的是「讓網站長出 agent 的能力」，客戶是開發者。

### 3.2 Agent 開發平台（按用量計價）

| 平台 | 計價單位 | 價格 |
|---|---|---|
| **CopilotKit** | thread（對話串） | 免費 200 / Pro **$39/月** / Team $100/席 |
| LangGraph Platform | compute unit | LCU $1.50、LSU $1.00；Plus $39/席/月 |
| Cloudflare Agents | 基礎設施用量 | 依 Workers/DO 計費 |

**CopilotKit 是架構上最接近的競品**（AG-UI 協定的作者，同樣解決 agent 與前端
UI 的溝通），而它的 Pro 正好是 **$39/月**。這表示 $39 對開發者是已被教育過的
價位帶，不需要重新說服。

值得參考的是 CopilotKit 的免費版設計：200 threads、**只保留 3 天**——
用保留期限而非數量當升級壓力。

## 4. 建議方案

**維持 $39 的價格點，但改以 token 計量。** 後端的 `MonthlyTokens` 已經是這個設計，
不需要新增計量機制。

| 方案 | 額度 | 價格 | LLM 成本 | 毛利率 | 約可對話 |
|---|---|---|---|---|---|
| Free | 100K token | $0 | $0.04 | — | 8–33 輪 |
| **Starter** | **1.5M token** | **$39/月** | $0.56 | 98.6% | **125–500 輪** |
| Pro | 5M token | $99/月 | $1.88 | 98.1% | 417–1,667 輪 |
| Ultra | 10M token | 客製 | $3.75 | — | 833–3,333 輪 |

「約可對話輪數」的區間下緣是工具密集（每輪 3 個工具、約 12,000 token），
上緣是純問答（每輪約 3,000 token）。**對外揭露時應同時標示這個區間**，
而不是只講上緣——那正是「500 則」的誤導之處。

Free 與 Ultra 沿用現有 `plans` 表的數字（100K / 10M），只新增中間兩級。

### 4.1 為什麼 token 比請求好

- **誠實**：使用者付的是實際成本的來源，不會有「以為 500 次結果只有 125 次」
- **誘因正確**：不懲罰使用工具
- **已經在跑**：`usage_events.total_tokens` 已在記錄，quota 已在 SUM
- **對齊產業**：LangGraph 從 node 改成 compute unit，同樣是因為「次數」無法反映成本

代價是**開發者較難預估自己會用多少**。緩解方式見 4.2。

### 4.2 配套：把 token 翻譯成人話

token 對使用者不直觀，所以介面上不能只顯示數字：

- Console 顯示「**已用 32%，約剩 340 輪對話**」，而非「已用 480,000 token」
- 估算用該 app 的實際平均值，而不是固定係數
- Playground 每次對話後顯示本輪消耗，讓開發者建立直覺

## 5. 額度模型設計

第 4 節談的是「賣多少錢」，這一節談「額度怎麼記、怎麼擋」。需求是同時支援
**請求數上限**、**token 上限**，並為**個別功能**預留各自的額度。

### 5.1 結論先講：ledger 已經支援，缺的是 plan 側

`usage_events` 當初就是為這件事設計的。`kind` 欄位的註解寫著：

> 'prompt' today; room for 'tool_call' or token-based units later without a
> schema change

也就是說，**要記什麼單位、要分幾種功能，資料表都不用改**。目前只是所有列都寫死
`kind = 'prompt'`，而 `usageSince` 只 `SUM(total_tokens)`、不分 kind。

真正缺的是 plan 那一側：`Plan` 目前只有一個 `MonthlyTokens` 純量，表達不了
「多個維度、每個維度各自有上限」。

### 5.2 資料模型

**三個正交的概念，不要混為一談：**

| 概念 | 回答的問題 | 存在哪 |
|---|---|---|
| **Meter（計量項）** | 要數什麼 | `usage_events.kind` + 要 SUM 哪個欄位 |
| **Limit（上限）** | 這個方案給多少 | Plan 的 map |
| **Usage（用量）** | 已經用了多少 | `usage_events` 的 append-only 帳本 |

計量項需要兩個屬性：**用什麼單位數**，以及**歸屬到哪個功能**。

```go
// Meter 是一個可獨立計量與設限的維度。
//
// Unit 決定怎麼加總：UnitCount 數列數（每列 +1），UnitToken 加總
// total_tokens。兩者共用同一張 usage_events，差別只在聚合方式，
// 所以新增一個 meter 不需要 schema 變更 —— 這正是 usage_events.kind
// 當初預留的用途。
type Meter struct {
    Kind string // 寫進 usage_events.kind，例如 "prompt"、"tool_call"
    Unit Unit   // UnitCount | UnitToken
    Name string // 對使用者顯示的名稱
}
```

**Plan 從純量改成 map：**

```go
type Plan struct {
    Tier  Tier
    Name  string
    // Limits 是每個計量項的每期上限。缺鍵 = 該項不設限，
    // 值為 0 = 完全禁用（兩者語意不同，不可混用）。
    Limits map[string]int
}
```

於是先前的 `MonthlyTokens: 1_500_000` 變成 `Limits: {"tokens": 1_500_000}`，
而要加「每月最多 500 次請求」只是多一個鍵，不動任何資料表。

### 5.3 建議的計量項

| Kind | 單位 | 為什麼要獨立計量 |
|---|---|---|
| `prompt` | count | 請求數上限（防濫用，見 5.4） |
| `tokens` | token | 真正的成本維度，付費方案的主要額度 |
| `tool_call` | count | 工具呼叫如果日後要收費或設限 |
| `backend_dispatch` | count | 後端派送會打第三方 endpoint，成本結構不同 |

前兩項是現在就要的，後兩項先定義、暫不設限（`Limits` 裡不放鍵即可）。

### 5.4 兩種上限的分工

同時有請求數與 token 上限，**不是重複設限，兩者防的是不同的事**：

- **token 上限**是**商業額度**——它對應真實成本，是使用者「買到的量」
- **請求數上限**是**濫用防線**——擋的是自動化腳本、無窮迴圈、壓力測試

所以兩者的數值不該按同一個比例換算。請求數應該訂得寬鬆許多（例如 token 額度
對應 500 輪，請求上限就給 5,000），**正常使用者永遠碰不到它，只有異常流量會撞上**。

若把請求上限訂得跟 token 額度一樣緊，就會重現第 1.1 節那個問題：工具用得多的人
被提早擋下。

### 5.5 檢查與記錄

**檢查**（`Check`）：逐一比對方案中定義的每個上限，任一超出即拒絕，並回報是
**哪一項**超出——錯誤訊息要能區分「token 用完了（請升級）」與「請求太頻繁
（請放慢）」，這是兩件完全不同的事，使用者的處置也不同。

**記錄**（`Record`）：一次 LLM round-trip 同時產生兩筆——一筆 `kind='prompt'`
（數次數）、一筆 `kind='tokens'`（記 token）。兩筆共用同一個 `event_id`。

這裡要留意現有註解已經說明的一點：`event_id` **不是 dedup key**，
`usageSince` 會把同 `event_id` 的多列加總。所以拆成兩筆不會互相污染——
只要聚合時有 `WHERE kind = ?` 就好。

### 5.6 聚合要改的地方

`usageSince` 目前寫死 `SUM(total_tokens)` 且不分 kind，需要改成依 meter 分派：

```sql
-- UnitToken
SELECT SUM(total_tokens) FROM usage_events
 WHERE owner_id = ? AND kind = ? AND created_at >= ?

-- UnitCount
SELECT COUNT(*) FROM usage_events
 WHERE owner_id = ? AND kind = ? AND created_at >= ?
```

**索引**：查詢條件從 `(owner_id, created_at)` 變成
`(owner_id, kind, created_at)`，需要對應的複合索引，否則每次檢查都會全表掃描。
這是這次改動唯一需要的 schema 變更（加索引，不動欄位）。

### 5.7 與訂閱快照的關係

第 6 節談到收錢後需要快照方案內容。`Limits` 是 map 而非純量，快照時直接存
JSON 即可：

```
subscriptions.limits_snapshot JSONB  -- 成交當下的 Limits 副本
```

讀取優先序：訂閱快照 → `plans` map → `FreePlan`。與現有 `PlanFor` 的
fallback 邏輯一致，只是多一層。

### 5.8 不要做的事

- **不要為每個功能開一張表。** `usage_events` 一張 append-only 帳本涵蓋所有維度，
  這也是現有設計「counter-free」的前提（見 quota 套件的 package 註解）。
  多張表會讓期間邊界與對帳變得極難維護。
- **不要用可變的計數器欄位。** 現有設計刻意避開 reset 邊界的 race，
  新增維度不該破壞這個性質。
- **不要讓 `Limits` 的缺鍵與 0 同義。** 缺鍵是「不設限」，0 是「禁用」。
  日後要做「免費版不能用後端派送」就靠這個區分。

## 6. 待決事項

**6.1 超額處理。** 兩個選項：

- **硬停**——實作最快（現有機制就是擋），但客戶的線上客服會突然啞掉
- **超額計費**——例如 $30/百萬 token（仍有 98% 毛利），體驗好得多

對外販售建議選後者，但需要新增計費流程。

**6.2 免費版的限制維度。** 目前 Free 是 100K token。是否比照 CopilotKit 加上
「對話保留 N 天」？保留期限是比額度更有效的升級壓力，且成本更低。

**6.3 「輪數」的對外定義。** 即使內部按 token 計，對外溝通仍需要一個直觀單位。
建議定義為「**一次使用者訊息觸發的完整回合**，含其中所有工具呼叫與 LLM 往返」。

**6.4 年繳折扣。** 尚未討論。業界慣例為八折（約兩個月免費）。

## 7. 方案要不要存進資料庫

現況是**只存 tier ID、方案值寫在程式碼的 `plans` map 裡**，訂閱紀錄不複製方案內容。
`plan.go` 的註解說明了它的好處：改一個數字全體立即生效，不用 migration、不用
backfill。

**在還沒收錢的現在，這是對的，不需要改。** 但開始收錢後會缺一塊。

### 7.1 兩種做法解決的是不同問題

| 做法 | 解決的問題 |
|---|---|
| 只存 plan ID | 「我要一次調整所有人的額度」——設定問題 |
| 值寫進訂閱紀錄 | 「這個人當初買的是什麼」——**帳務問題** |

關鍵在於：**方案定義會變，但已經發生的交易不能變。**

假設 Starter 是 1.5M / $39，有人訂閱了；三個月後調成 1.2M / $49。若只存 tier ID：

- 這個人的額度會**自動變成 1.2M，且被收 $49**
- 他客訴「我買的時候是 1.5M」，你**查不出他是對是錯**
- 想給早期用戶保留舊價（grandfathering）也做不到

`subscriptions.monthly_quota` 其實已是這個方向的雛型——註解指出它「today has no
write path at all」，存在的理由正是 per-user override。

### 7.2 業界做法：ID 指向不可變的東西

Stripe 的三層模型可直接參考：

| 層 | 角色 | 可變性 |
|---|---|---|
| Product / Price | 方案定義 | 改價 = 新建 Price，**舊的永不修改** |
| Subscription | 誰訂了哪個 Price | 指向一個不可變的 Price |
| Invoice | 這次實際收了多少 | 完全快照 |

所以嚴格說是第三種答案：**存 ID，但那個 ID 指向的東西不可變。**

### 7.3 建議

**現在**：不動。`plans` map 夠用，導入版本化只是徒增複雜度。

**開始收錢時**：最小改動是在訂閱建立時快照當下的方案內容（見 5.7 的
`limits_snapshot`），讀取優先序為 訂閱快照 → `plans` map → `FreePlan`。

**快照什麼、不快照什麼**，判準很簡單：

- **影響金錢與承諾的** → 快照（額度、價格、計費週期）
- **純粹呈現或行為的** → 不快照（方案名稱、功能開關、UI 文案）

方案名稱從「Starter」改叫「基礎版」，不該去改一萬筆訂閱紀錄。

這個折衷不需要新的 plans 資料表：`plans` map 仍是新訂閱的預設來源，已成交的訂閱
則有自己的依據。代價是「全體調整額度」變麻煩——但收錢之後**本來就不該任意調整
已付費用戶的額度**，所以這個代價其實是正確的約束。

## 8. 一個反面意見：$39 可能定太低

單看成本，這個定價非常安全。但從價值看，它可能低估了自己。

客戶用 onagent 省下的是客服人力。一個客服月薪至少 NT$35,000；即使只取代 10% 的
工作量，價值也是 NT$3,500 ≈ **$111**。收 $39 等於把三分之二的價值讓出去。

這正是 Fin 敢收 $0.99/則的原因——**那一則省下的人力值那麼多，跟 token 成本無關**。
這個市場的定價與成本幾乎脫鉤。

不過，**初期以低價換取用戶與案例是合理策略**。若這是刻意的選擇，$39 沒有問題；
但條款上應保留調價空間，不要承諾終身價。
